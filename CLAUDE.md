# Demo: fintech onboarding experiment (Chip-branded, reusable)

## Purpose

Show a PM audience an onboarding experiment end to end in LaunchDarkly: create an experiment from an existing flag, see two variations on a realistic flow, read results, understand why conversion attribution broke before and what to ask engineering for, and when to measure in LaunchDarkly vs. Databricks. Demo date: Nov 24/25, 2026.

Audience constraint: product managers. The LaunchDarkly UI and the onboarding flow are what they will look at. The architecture runs underneath and must be correct, not visible.

Working rule: follow the build order below. Do not wire a later step into an earlier one. Decisions listed under "Decisions" are settled; ask before changing any of them. Commit at the end of each build-order step with a message naming the step.

Default brand (`brand.json`): **Launchpad** — legal name "Launchpad Wealth Ltd", a fictional UK app-only savings and investing app. A second config for another fictional brand must work with no code change; a customer-named config may be added later.

## Stack

- `client/` — React + Vite, phone-framed (390x844 viewport inside a device chrome), LaunchDarkly JavaScript client SDK (or the React wrapper). Stand-in for the customer's native iOS/Android app.
- `server/` — Node + Express, LaunchDarkly Node server SDK. Stand-in for the customer's backend. Owns KYC and deposit confirmation.
- `sim/` — Node traffic simulator that drives synthetic users through the flow against the real SDKs.
- `brand.json` — all customer-facing naming, palette, products, copy. Chip version first; swapping it must require no code changes.
- Databricks — Delta table written by the server; warehouse-native metric configured in LaunchDarkly. Behind an env flag (`DATABRICKS_ENABLED`) so the demo runs without it.

Secrets live in `.env` (never committed). Provide `.env.example` with placeholder names:
`LD_CLIENT_SIDE_ID`, `LD_SDK_KEY`, `DATABRICKS_HOST`, `DATABRICKS_TOKEN`, `DATABRICKS_WAREHOUSE_ID`, `DATABRICKS_ENABLED`.

## Onboarding flow (client screens)

1. Welcome
2. Create credentials (email + password) → `POST /signup` returns `userId`
3. Identity check (KYC) → `POST /kyc`, simulated async: pass (default), fail, manual review
4. Link bank (simulated Open Banking consent) → `POST /bank-link`
5. Choose product (from `brand.json`: Easy Access, Cash ISA, Prize Savings, Stocks & Shares ISA, Pension)
6. **First deposit prompt — the experiment surface** → `POST /deposit`
7. Done

## Contexts (must be right)

- On app load: anonymous `device` context, key auto-generated by the SDK and persisted in localStorage (stands in for the mobile SDK's on-device key).
  `{ kind: 'device', key: <auto>, anonymous: true, platform: 'ios' | 'android' (randomized) }`
- After signup: `identify()` with a multi-context: the same `device` plus `{ kind: 'user', key: userId }`. The device key never changes within a session.
- **Randomization unit for the experiment: `device`.** Comment in code why: onboarding starts before a user exists.
- Every server call that can produce a conversion carries the full LaunchDarkly context in the request body. The server tracks against *that* context, never against a user ID it constructs itself. This is the attribution fix the demo exists to show.

## Flags

### `onboarding-deposit-prompt` — JSON flag, the experiment

Variations:
- `control`: `{ "variation": "control", "headline": "Make your first deposit", "amounts": [10, 25, 50], "framing": "start-small" }`
- `earn-first`: `{ "variation": "earn-first", "headline": "Start earning 4.55% today", "amounts": [100, 500, 1000], "framing": "rate-led" }`

Rules:
- Evaluated **only** when screen 6 renders. Not at app load, not in a bulk read of all flags into state. One evaluation, one exposure.
- The server **never** evaluates this flag. If the server needs the variation (e.g., validating amounts), the client sends it.

### `onboarding-deposit-step` — boolean kill switch (in scope, built last)

Off state renders a fallback message: "Deposits are temporarily unavailable — your account is ready and we'll let you know." Covers the release-risk / fallback-without-redeploy story.

### Flag setup spec (create exactly this, via MCP or by hand, then verify in the UI)

Project: `launchpad-wealth`. Environment: the one whose keys are in `.env` (default `production` unless `.env` says otherwise).

**`onboarding-deposit-prompt`**
- Name: "Onboarding – first deposit prompt"
- Type: JSON (multivariate), permanent flag
- Variations (name → value):
  - `control` → `{ "variation": "control", "headline": "Make your first deposit", "amounts": [10, 25, 50], "framing": "start-small" }`
  - `earn-first` → `{ "variation": "earn-first", "headline": "Start earning 4.55% today", "amounts": [100, 500, 1000], "framing": "rate-led" }`
- Default variation when flag is ON: `control`. When OFF: `control`.
- Client-side availability: **SDKs using Client-side ID = ON** (`clientSideAvailability.usingEnvironmentId: true`). Mobile key = ON too (harmless, mirrors the customer's native apps).
- Targeting: ON. No individual targets, no rules. Default rule serves `control`. The experiment will own the traffic split later — do not add a percentage rollout.
- Tags: `demo`, `onboarding`, `experiment`

**`onboarding-deposit-step`** (built last)
- Name: "Onboarding – deposit step kill switch"
- Type: boolean, permanent flag
- Variations: `true` = "Deposit step available", `false` = "Deposit step disabled (fallback message)"
- Default when ON: `true`. When OFF: `false`.
- Client-side availability: SDKs using Client-side ID = ON
- Targeting: ON, default rule serves `true`
- Tags: `demo`, `onboarding`, `kill-switch`

If a flag evaluates to its code default in the client, check client-side availability before debugging code.

## Metrics (LaunchDarkly-tracked via server `track()` on the client's context)

- `account_created` — fired on KYC pass. Conversion metric, unit = device. Guardrail / secondary.
- `deposit_confirmed` — fired on deposit confirmation with `metricValue = amount`. Two LaunchDarkly metrics on one event: a conversion metric (did they deposit) as **primary**, and a numeric metric (amount) as secondary. The numeric one will look noisy; that is intentional and is the segue to Databricks.
- Optional client-side funnel events for the LaunchDarkly funnel view: `kyc_started`, `bank_linked`, `product_selected`. Not outcomes.

## Databricks (warehouse-native)

- Server writes every exposure (relayed from the client at screen 6) and every conversion to a Delta table `onboarding_events` with columns `event_ts, event_name, device_key, user_key, variation, amount, platform, simulated`.
- Configure a LaunchDarkly warehouse-native experiment against this table for the deposit-amount metric. Follow current LaunchDarkly documentation for the required exposure and metric table schemas; build the writer to those schemas directly so there is no transform step.
- Demo beat: same experiment, amount metric from LaunchDarkly events vs. from Databricks.

## Simulator (`sim/`)

- Generates N synthetic devices (mix of iOS/Android), each walking the API with a real multi-context. Evaluates `onboarding-deposit-prompt` via the server SDK per device to produce assignment and exposure, then posts conversions through the server endpoints so the tracking path is identical to real users.
- Variation-dependent probabilities: `earn-first` gets a modest lift on deposit rate and a larger lift on amount, with a heavy tail (a few 5k–20k deposits). KYC fail rate ~8%, manual review ~4%, so Accounts Created < signups.
- Tag every context `simulated: true`.
- Runs Friday night and over the weekend so results are populated by Monday.

## Acceptance checks

- One exposure per device per session in LaunchDarkly, none from the server.
- A deposit confirmed by the server shows against the same device the client was exposed under.
- Swapping `brand.json` for a second fictional fintech changes every visible string and color with no code edit.
- The experiment results page in LaunchDarkly shows both deposit metrics populated with simulated data by Monday morning.

## Decisions (settled — do not revisit without asking)

1. **LaunchDarkly project:** fresh project `launchpad-wealth`, created manually in the LaunchDarkly UI. Flags are created from the "Flag setup spec" in this file, either via the LaunchDarkly MCP or by hand, and verified in the UI before any code depends on them. Code uses the keys in `.env`; never create projects, environments, metrics, or experiments from code.
2. **Simulator:** runs in a continuous loop (configurable interval and batch size) from Friday evening through the demo so results keep arriving live. Must be safe to stop and restart without duplicating a device's exposure.
3. **Kill switch flag `onboarding-deposit-step`:** in scope, built last — after the Databricks writer, before Monday polish.
